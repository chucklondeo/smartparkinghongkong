**Root cause of the lint/build hang:** `app/layout.tsx` uses `next/font/google` (`Inter`), which requires Next.js to fetch font files from `fonts.googleapis.com` / `fonts.gstatic.com` at build time. This sandbox's outbound network proxy returns `403` for both hosts (confirmed directly with `curl`), while `github.com` and `registry.npmjs.org` are reachable. Next.js does not fail fast on this — it hangs. **This is an environment limitation of the Cowork sandbox, not a bug in the repository.** The build should be re-verified in a normal developer machine or CI runner (GitHub Actions itself already builds successfully there, per the commit history in §6). If it's useful long-term, self-hosting the Inter font file (instead of `next/font/google`) would remove this external dependency entirely and is worth considering as a small resilience improvement — not applied in this pass.

`next lint` also prompts interactively for ESLint setup on a fresh checkout (no `.eslintrc*` file exists in the repo) — worth adding a checked-in ESLint config so `next lint` runs non-interactively in CI and locally. Not applied in this pass (see §7).

## 4. Confirmed findings — information architecture

This is a **single-page site**. Everything lives on `/`. Confirmed by:

- `app/` contains only `app/page.tsx`, `app/layout.tsx`, `app/globals.css` — no other route segments.
- The static export (`out/`) contains only `index.html`, `404.html`, `index.txt` and `_next/` — no other pages were ever generated.
- `public/.htaccess` includes an SPA-style fallback: any request that isn't an existing file/directory is rewritten to `/index.html` (`RewriteRule ^ /index.html [L]`).

**Direct consequence:** `/products`, `/solutions`, `/about`, `/contact`, etc. do not 404 — Apache serves `index.html` with an HTTP 200 for all of them, exactly as flagged in the original brief. This also means `/robots.txt` and `/sitemap.xml` do not currently exist (confirmed — no such files anywhere in `public/`, `app/`, or the last `out/` build), so those too would silently fall through to the homepage under the current `.htaccess` rule.

**Navigation is not link-based.** `components/Navigation.tsx` and `components/Footer.tsx` build their menus from `<button onClick={() => document.querySelector(href)?.scrollIntoView(...)}>` — anchor-scroll only, not `<Link>`/`<a href>`. This means: no keyboard/no-JS access, nothing for a crawler to follow as a real URL, and no active/current-page state beyond scroll position.

**Privacy Policy / Terms of Service are non-functional.** In `components/Footer.tsx` (lines ~107–108), both render as `<button>` elements with **no `onClick` handler at all** — confirmed dead buttons, exactly as described in the original brief.

## 5. Confirmed findings — lead capture

- `components/Contact.tsx` submits directly from the browser to Supabase: `supabase.from("contact_submissions").insert({...})`, using the public/publishable Supabase key (`lib/supabase/client.ts`). This is a legitimate pattern for a static-export site, but as implemented today it has **no honeypot field, no rate limiting, and no server-side validation** — anything reaching the browser can write to that table directly.
- On success, the form shows an inline "Message Sent!" state — there is **no redirect to a `/thank-you` page** (that route doesn't exist).
- Required fields today: `name`, `company`, `email` (text `required`), `projectType` (`required` select). `whatsapp` and `message` are optional. This is close to, but not identical to, the brief's target rule ("Name, Company, Email-or-WhatsApp, Enquiry Type required").
- The displayed WhatsApp number, `+852 XXXX XXXX`, is a **literal placeholder string in the code** (`components/Contact.tsx`) — not a real, clickable `wa.me` link, and not a real number. Flagged in `docs/content-required.md`.
- No lead source/UTM/product-context capture exists in the insert payload today.

### Update — after `git pull --ff-only` to `f53a99c` (your own recent work)

While walking through the Git setup, you pulled `main` forward from `bbdb226` to `f53a99c` on your machine, which included work you/your team did after the original audit above. This changes §5 in three ways — confirmed by re-reading the updated files directly:

2. **A new Supabase Edge Function, `supabase/functions/send-contact-email/index.ts`, was added** (calls the Resend API to email `sales@londeoaccess.com.hk`) **but nothing in the frontend calls it.** It's a complete, reasonable implementation — CORS handled, required-field check, HTML+text email — just not wired to `Contact.tsx` yet.

You've confirmed (in conversation) that the intended direction is to route the form back through the existing `send-contact-email` Edge Function rather than FormSubmit — see `docs/website-rebuild-plan.md` §7 for the updated recommendation.

`public/.htaccess` was also updated in this same pull: the www/non-www redirect direction flipped from "www → non-www" to **"non-www → www"**, which now correctly matches the `https://www.londeoaccess.com.hk` canonical already used in `app/layout.tsx` metadata. This is a genuine fix, not a regression. The SPA-fallback rule that sends unknown paths to `index.html` with a 200 (§4) is still present and unchanged.
